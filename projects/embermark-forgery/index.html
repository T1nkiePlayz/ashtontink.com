Embermark Forgery.

A cozy-yet-tense 2D smithing game written in Rust + Bevy. Heat the metal, read the colour, strike on the beat and inscribe living sigils into steel — then sell your work to a town that remembers what you forge.

// overview

Small enough to finish, big enough to learn.

Embermark Forgery exists for a practical reason: building a huge game like Aetheria is very different from finishing a smaller one. This project gives me a contained space to practise the complete development process — deciding what belongs, implementing mechanics, creating content, testing, fixing, polishing and working toward a release.

The loop is deliberately short and physical: it is a game about one craft, done well, rather than a world full of systems nobody has time to build.

// the_loop

Heat, hammer, quench, inscribe.

  • Heat — hold Space on the bellows and watch the metal climb into its working band.
  • Hammer — tap on the beat; timing inside the green zone becomes the item's quality grade.
  • Quench — one precise hit to lock the work in, or ruin it.
  • Inscribe — draw an Embermark sigil into the finished steel.
  • Sell or keep — commissions have requirements, and the town remembers what you forge.
// architecture

Engine-agnostic where it counts.

The simulation core — crafting rules, materials, blueprints, sigils — is deliberately kept free of Bevy imports, so the interesting logic can be tested without a window. cargo test runs 15 headless tests over the simulation and its data.

Tuning lives in plain JSON under assets/data/: materials, blueprints and marks are edited as data, not recompiled as code.

// documentation

Built in the open, step by step.

The repository ships two long-form documents: BUILD.html, a guided, milestone-by-milestone walkthrough of how the whole project was made — twelve steps from cargo new to a tested, playable game, each ending in a runnable checkpoint — and DESIGN.html, the full game design document that every module implements.

// why_rust

Rust, not Godot this time.

The first version of this project lived in a scene engine. Rewriting it in Rust + Bevy turned the game into a codebase I fully control — and made the borrow checker part of the design process rather than an afterthought.

// lessons

What I'm practising.

  • Scoping a project realistically
  • Separating simulation from rendering
  • Data-driven tuning and content pipelines
  • Testing logic that normally needs a game running
  • Game feel: timing, feedback and sound
  • Balancing code and content
// relationship

Before Aetheria.

Embermark isn't intended to replace Aetheria. It is a smaller step that lets me practise shipping and learn from mistakes before applying those lessons to a much larger project — and it doubles as my Rust practice ground.

// project_note

A smaller project can teach bigger lessons.

The point is to experience the parts of game development that only become obvious when you try to turn an idea into a complete game — and to have something playable at the end of it, rather than a folder of foundations.
